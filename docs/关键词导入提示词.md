# 将现有关键词 DB 直接导入 review.db 的提示词

首次创建空历史的正式库请优先使用 [正式环境初始化](正式环境初始化.md) 中已实现的 setup.py；以下提示词适用于向已有 review.db 追加或更新关键词。

复制以下内容交给能访问原关键词数据库的本地 AI：

---

请在 `D:\Projects\ai_review_unit_test` 项目中编写并验证一个离线 Python 脚本，把我现有 SQLite 关键词数据库中的记录直接导入 `D:\Projects\ai_review_unit_test\data\review.db` 的 `keywords` 表。直接通过项目 SQLAlchemy Session 操作目标数据库，不经过 HTTP API。先阅读项目代码和适用的 AGENTS.md。

我的源数据库路径：`<在这里填写关键词 DB 的绝对路径>`；源表名：`<在这里填写表名>`。如果未填写，请只问我这两个信息，不要猜测。源库是独立文件，不能覆盖或替换 review.db。

源数据库中 A、B、C、D 四个 TEXT 字段构成联合主键，I 字段是唯一的关键词字符串，不是数组。请先以只读方式检查我本机的源数据库、实际表名和字段名；如无法确定源文件，仅向我询问源数据库路径和表名。不要修改源库。

字段映射必须如下：

| 源字段 | 业务含义 | 目标 payload 字段 |
|---|---|---|
| A | 测试对象 | a |
| B | 用例编号 | b |
| C | 用例名称 | c |
| D | 测试小项 | d |
| I | 关键词（单个字符串） | e |

目标不是把源文件替换为 review.db，也不是给 review.db 添加 A～I 物理列。项目 `keywords` 表已有 `id/domain/key/payload/version/deleted`，五个业务字段保存在 JSON `payload` 中，例如 `{"a":"对象","b":"001","c":"用例","d":"小项","e":"关键词"}`。

请复用以下规则，禁止自行拼接主键或另建一套匹配逻辑：

- `backend/app/keywords.py` 的 `ENTRY_DOMAIN` 和 `entry_key(payload)`；当前 domain 为 `__five_column_keywords__`，key 为 a～d 的 JSON 数组经 SHA-256 得到的稳定值。
- `backend/app/schemas.py` 的 `KeywordEntry` 校验。A～D 必须保持原始 TEXT 内容，不能 trim、转数字、补零或改变大小写。I 必须是非空白字符串。NULL、重复联合键、无效数据必须明确报告，不能静默转换。
- `backend/app/services.py` 的 `apply_change` 负责版本递增、记录变更和使受影响的测试项变为待审查。不能直接覆盖 payload 绕过这些行为。

每条源记录转换为以下目标结构。`id` 使用项目 UUID 生成方式，`key` 调用项目函数生成，`payload` 使用 SQLAlchemy JSON 字段写入对象，不要再次 json.dumps 导致存成 JSON 字符串：

```json
{
  "id": "项目生成的 UUID",
  "domain": "__five_column_keywords__",
  "key": "entry_key(payload) 的返回值",
  "payload": {"a": "对象", "b": "001", "c": "用例", "d": "小项", "e": "关键词"},
  "version": 1,
  "deleted": false
}
```

使用 `--admin-user` 参数指定目标 users 表中已有的有效管理员用户名，检查 role=admin 且 active=true，不能凭空创建管理员。对需要新增或修改的记录，直接在同一 SQLAlchemy 事务中创建 `ChangeRequest`，调用 `apply_change(db, change, admin)`，再标记为 approved、reviewer_id 为该管理员、review_note 为“管理员本地导入直接生效”，reason 为“本地关键词库导入”。沿用项目变更留痕和待审查状态更新逻辑，无需登录 API 或读取用户密码。

读取目标 `keywords` 表（包括软删除记录）和未决 `change_requests`。已存在且内容相同则跳过；同主键但关键词不同，必须显式启用 `--update-existing`，使用当前 version 作为 base_version，action 为 update。遇到 deleted=true 的历史关键词、同主键的 pending 审批申请、重复源键或无效数据时，报告冲突并拒绝整批写入，不能擅自恢复、删除或替换。

脚本支持 `--source`、`--table`、`--target`、`--admin-user`、`--apply`、`--update-existing`。默认 dry-run，只统计新增、相同、待更新和冲突；明确指定 --apply 才写入。正式导入前停止 API 和 Worker，使用 SQLite backup 接口备份目标库，源库使用 mode=ro 连接。核验两个数据库均已存在且不是同一文件，禁止连接错误路径后自动创建空库；表名从源库 sqlite_master 校验并正确引用。整个写入放在一个事务中，任何错误全量回滚，不能部分导入。

执行前后核对行数和主键匹配；验证重复执行不新增重复记录、前导零和中文原样保留、空字符串联合键按项目规则处理、无效关键词拒绝、更新后相关测试项变为待审查。完成后重启系统，检查网页能查到关键词，并通过四个测试字段匹配到 I 字段原始关键词。

本次目标明确为 `D:\Projects\ai_review_unit_test\data\review.db`，通过 --target 显式指定；同时核对项目 `.env` 的 DATABASE_URL 是否指向它。若不一致先报告，避免导入后网页读到另一个数据库，不要直接修改 `.env`。原数据库、备份、Excel、`.env` 和 `backend/local_adapters` 下的文件都不能提交 GitHub。导入工具保存在已被 Git 忽略的 `backend/local_adapters/import_keywords_db.py`，敏感映射配置也只保留本地。
